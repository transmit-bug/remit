# 插件系统 · 宿主 API v1

一张地图（#69）收口用的设计稿。每条选择都标了出处——参照主流做法，不发明新机制。

## 1. 五条原则

| 原则 | 出处 | 我们怎么落 |
|---|---|---|
| **静态声明 + 惰性激活** | VS Code：`contributes`（静态）+ `activationEvents`（何时加载） | manifest 用**宿主定义的钩子词汇表**声明 `implements` 与 capabilities；宿主不启动插件即可展示、校验与索引它的全部表面 |
| **能力即对象，不是权限弹窗** | Obsidian：没有沙箱，API 面（Vault / MetadataCache）本身就是边界 | JS 全局只有 `remit`，标准库冻结；拿不到 `fs` / `net` / 定时器以外的宿主能力 |
| **安装时授权，运行时不再问** | VS Code：扩展信任在安装时建立 | 启用插件时展示它声明的 capabilities 并让用户批准；运行期只安装已批准的 `remit.*` |
| **插件失败不得阻塞主流程** | Anki：add-on 出错不影响复习 | 抛错/超时/内存超限 → 回退**内置默认插件**，计数，三次停用 |
| **内置也是插件** | VS Code：built-in extensions 走同一 API，无特权 | 默认制卡/渲染/调度随应用打包，同样走 manifest 与 capability |

**不要 legacy 双实现**：插件路径跑通、金标准 fixtures 全绿之后，删除 core 里的 Go 实现（#77）。

## 2. 包与 manifest

```
<App data>/extensions/<id>/
├── extension.json
└── main.js          # 单文件 ES module；多文件走宿主解析的模块图，不读磁盘其它位置
```

```json
{
  "id": "remit.cards.standard",
  "name": "Standard cards",
  "version": "1.0.0",
  "apiVersion": 1,
  "runtime": "js",
  "entrypoint": "main.js",
  "capabilities": ["notes:read", "cards:write", "review:read", "schedule:fsrs"],
  "implements": { "cards.derive": 1, "cards.render": 1, "review.schedule": 1 },
  "activation": ["onReview", "onNoteSaved"],
  "contributes": { "settings": [] }
}
```

- `implements` 的键是**宿主词汇表里的钩子 ID**，值是**该钩子的契约版本**。导出函数名由宿主固定（`deriveBlock` / `renderCard` / `scheduleGrade`），插件不能自定义——这样宿主可以在不加载插件的情况下校验它「声称实现了什么」，也避免 Anki 那种「运行时追加的全局钩子列表」退化成的隐式顺序契约（研究 #70）。
- `activation` 只决定**何时加载**，不决定加载谁——角色（derive/render/schedule）决定谁被选中。
- `contributes.settings` 声明**由宿主渲染**的设置项（插件不做 UI，见 #9）。v1 允许为空数组。

## 3. Hooks 与数据契约

三个纯函数 + 一个事件回调。纯函数不得写库，写入只能通过 capability，由宿主在 hook 返回后应用（与仓库现有的 immediate-mode 纪律一致）。

```ts
type Block = { id: string; noteId: string; text: string; title: string }
type Grade = 1 | 2 | 3 | 4                 // again | hard | good | easy

// derive：一块文本 → 若干卡片（ADR 0002：`::` 前提示、后答案；空则整块为提示）
export function deriveBlock(block: Block): Array<{ front: string; back: string }>

// render：卡片 → 两段 markdown（宿主用 ui/markdown 渲染，插件拿不到渲染器）
export function renderCard(card: { id: string; blockId: string; front: string; back: string }):
  { frontMarkdown: string; backMarkdown: string }

// schedule：评分 → 间隔与预览。FSRS 数学在宿主，插件只给策略
export function scheduleGrade(input: {
  cardId: string; grade: Grade; now: string;
  state: unknown;                           // 宿主拥有、插件不可解释，原样传回
}): { intervalSeconds: number; state: unknown; previews?: Record<Grade, number> }
```

**为什么 state 不透明**：FSRS 在宿主（`remit.fsrs.*`），插件能做的是策略（步长、上限、fuzz、降级）。state 一旦让插件解释，就等于把调度数学又复制一份。

## 3.5 产出即建议

- 三个钩子的返回值都是**建议**：宿主校验结构、夹取边界（间隔上限、非负）、然后由宿主自己写库。插件永远不直接写。
- 每条派生数据都带**生产者标识与版本**（`producer: {id, version}`），卸载插件后数据仍可读、可解释（研究 #70 的第三条"该抄"）。
- 渲染钩子的产出**不落库**：每次从卡片数据重新渲染；渲染插件缺失时回退到块的原文，而不是空白。

## 4. Capabilities

| 能力 | 授予的宿主面 | 拒绝时 |
|---|---|---|
| `notes:read` | `remit.notes.list/get/search` | hook 抛 `CapabilityError` |
| `cards:write` | `remit.cards.create/update/delete` | 同上 |
| `review:read` | `remit.review.history/dueCount` | 同上 |
| `review:write` | `remit.review.record` | 同上 |
| `schedule:fsrs` | `remit.fsrs.review(state, grade, now)` | 同上 |
| `store:own` | `remit.store.get/set`（命名空间绑定到插件 id） | 同上 |

**没有** `fs` / `net` / `ui` / 任意 SQL。需要联网的插件是 v2 议题（那时加 `net:fetch` + allowlist）。

## 4.5 爆炸半径（与 #9 的差异，必须写进 ADR）

`#9` 用「独立进程 + 只能经协议改状态」把插件出错的爆炸半径压住；进程内 JS 换了这份隔离。补偿是三件事：能力面（拿不到 `fs`/`net`/`ui`）、`Interrupt`（19–25 µs 打断）、`MemoryLimit`（真实拦停）。**但不能声称等价**：引擎自身的内存安全 bug 仍会带崩 app。这一点由 #68 的 ADR 0006 记录为已知风险，不靠"沙箱"两个字带过（研究 #70 的"不该抄"第一条）。

## 5. 错误、超时、内存、停用

| 情况 | 宿主行为 |
|---|---|
| 抛异常 | 记一次失败；该 hook 回退内置默认插件；错误写进插件日志 |
| 返回结构非法 | 同上，错误信息标 `invalid result` |
| 超过 1s | `rt.Interrupt`；记一次失败 |
| 超 64 MiB | `ErrMemoryLimit`；记一次失败 |
| 连续 3 次失败 | 停用该插件，通知用户，复习继续走内置默认插件 |
| 加载失败（语法错） | 只影响该插件；库照常打开 |
| 渲染插件缺失 | 卡片面回退到块的原文（`::` 切分后的两段），不显示空白 |

`#67` 实测：打断死循环 19–25 µs，host panic 返回 `*InternalError` 且进程存活。

## 6. 版本

- `apiVersion`：整数，是**契约产物 `remit.d.ts` 的版本**（与 VS Code 的 `vscode.d.ts` 同位）。宿主按**最低版本**语义接受：插件声明的 `apiVersion` ≤ 宿主即可加载，不要求精确匹配（`#9` 的 `protocol: 1` 精确匹配只能硬失败，这是要改掉的地方——研究 #70）。
- 破坏性变更 +1；旧版插件继续可用一个大版本（deprecation 窗口），之后拒绝加载。
- `protocol`（#9 的 exec 线协议）与 `apiVersion`（JS 宿主面）分开：前者是传输，后者是数据契约。
- 复习记录里写 `scheduler: { id, version }`：换调度插件后历史仍可读，只是不再可比（#72 的规则）。

## 7. 生命周期

```
discovered → enabled(能力已批准) → loaded(惰性) → failed(n) → disabled
                    ↑                                  │
                    └──────── 用户手动重新启用 ←────────┘
```

- 启用是**按库**的显式动作（沿用 #9），批准发生在启用时。
- 选中关系：每个角色（derive/render/schedule）每库选定**一个**插件，默认是内置默认插件。多个插件声明同一角色时不自动仲裁，由设置页选择。

## 8. 内置默认插件与"No legacy"

- 位置：`resources/plugins/remit.cards.standard/`（`//go:embed`），走与三方插件相同的加载路径、相同的 capability 检查，**没有特权入口**。
- 删除条件（写进 ADR 0007）：金标准 fixtures 全绿 + 内置默认插件成为唯一实现。
- 回退 = 回退到它，不是回退到第二份 Go 代码。

## 9. 怎么测一个插件

`go tool remit ext test <dir>`：用 fixtures（笔记 + 复习历史）跑全部 hook，逐字比对输出。同一套 fixtures 也是 #77 删除 Go 实现时的凭据。

## 10. v1 不做

插件市场 / 签名 / 自动更新 · 插件注入 UI · `net:fetch` · 插件间依赖 · 移动端。

[`GLOSSARY.md`](../../GLOSSARY.md) 与[插件面稿](plugins/system.md)；结构词（模块、接口、实现、深度、接缝、适配器）
取自 `codebase-design`。

本稿与 [`docs/specs/plugins/system.md`](plugins/system.md)、ADR 0006 / 0007 / 0008 冲突时以后者为准——
本文是待修订的设计稿，不是已接受的决定。§1–§10 是 v1 定稿前的旧稿，其中 `cards.render`、
`entrypoint`、`resources/plugins/` 已被现行为取代。

评审实测到的现状，各则直接或间接修它：

| # | 现状 | 后果 |
|---|---|---|
| A | 角色的 runner 在库打开**之前**启动（调度策略要在索引重放前就位），拿到的宿主是 nil；库打开后 `SetLibrary` 把它们关掉并从缓存里清掉 | 窗口手里的那个 runner 从此既没宿主、也已关闭——能力调用一律失败，而它正是渲染路径用的那一个 |
| B | 切库不重新解析角色 | 新库沿用上一个库的插件；`store.Open` 的调度参数也来自上一个库的插件 |
| C | 启用列表与角色两条路径各启动一份 runner | 同一插件两份 runtime 池，两处写 `plugins-data/<id>.json` |
| D | 连续三次失败停用，但没有任何读者 | ADR 0007 的“停用并告知”只做了一半 |
| E | 上下文十二个键声明五遍 | 回调 payload 少三个键 |
| F | 派生答案的缓存随每次写入被重建 | 键里没有插件身份与类型指纹，命中率近乎零 |
| G | 插件页的一生是窗口上的七个方法与八张表 | 规则没有接口，只能造一个窗口来测 |
| H | 派生的入口被建了四份：窗口一份用角色插件，智能体 API、插件能力、插件宿主各一份都直接开**内置**制卡插件 | 用户换的制卡插件只在窗口里生效，API 与 `remit.cards.create` 仍按内置规则制卡 |
| I | 智能体 API 的 Resolver 被 HTTP 处理 goroutine 共享，而它的缓存 map 无锁读写 | `-race` 下并发请求就红；Go 的 map 并发写会直接 panic |

## P1 · 插件 supervisor：一个所有者、一个 runner

### Problem Statement

今天的插件系统只在“切库”那一刻真正启动。用户装了一个第三方制卡插件并选它做制卡角色：启动应用，
它启动得比库还早——调度策略得在索引重放之前就位——于是它拿到的宿主是 nil。库打开后宿主确实装上了，
但装在了“把已有 runner 关掉并清空”这一步上：窗口手里那个 runner 既没宿主、也已关闭。
插件读不了库、写不了自己的存储；纯钩子（派生、策略）看不出来，因为错只在能力调用上显形。

还有一条更隐蔽的：实现派生的模块只有一个，但它被实例化了四份。窗口一份（用角色选的插件），
智能体 API、插件能力、插件宿主各一份，后三份都直接开内置制卡插件。于是用户换了自己的制卡插件，
从 API 或从插件里制出来的卡仍按内置插件的规则，producer 戳也盖的是内置插件的。

切库时又反过来：窗口不重新解析角色，还顺手关掉上一个库的 runner。
一个既被启用、又扮演角色的插件于是有两份 runner、两份 runtime 池，两处写同一个插件存储。

设置页也无法回答“这个插件怎么了”：失败三次停用是实现了的，但没人读那个状态，也不告诉用户。

### Solution

一个 supervisor 模块做插件的唯一所有者：发现、启用列表、角色解析、**每个插件名一个 runner**、预热、
失败计数与停用、库切换时换宿主、关库时关闭。窗口只问它要角色与 runner，不再自己判断怎么启动一个插件。

### User Stories

1. 作为写笔记的用户，我希望应用一启动就能从段落里制卡，而不需要先切一次库来让插件醒过来。
2. 作为复习的用户，我希望调度插件在库被读入之前就确定，这样到期时间是插件算的，不是默认策略算的。
3. 作为装了第三方制卡插件的用户，我希望它作为角色插件时也能读库、也能写自己的存储，而不是只有它的页面能读。
4. 作为装了大量插件的用户，我希望一个插件在一份库里只启动一次，这样它的存储不会被两个 runner 争着写。
5. 作为用户，我希望插件连续失败三次之后，设置页明确告诉我它被停用了、为什么、怎么恢复。
6. 作为用户，我希望插件坏掉时库照常打开、复习照常进行，卡片读它自己的段落文字。
7. 作为用户，我希望换一个库之后，插件的角色按新库的配置重新解析，而不是沿用上一个库的插件。
8. 作为插件作者，我希望我声明过的能力在每一份库里都可用，而不是取决于用户是不是第二次打开它。
9. 作为插件作者，我希望我的插件被停用后能被用户显式重新启用，而不是要重启应用。
10. 作为插件作者，我希望“内置也是插件”是真的：内置插件和我的一样走发现、校验、能力、限制。
11. 作为维护者，我希望插件的一生只有一个所有者，这样我改生命周期不用改五个文件。
12. 作为维护者，我希望首次开库与切库走同一条路径，这样它们的差异不再是缺陷的来源。
13. 作为维护者，我希望窗口的构造参数里不出现加载器的具体类型，这样窗口能在没有引擎的情况下测试。
14. 作为测试者，我希望用一个假 runner 就能测角色解析、失败停用与库切换，不必启动 JavaScript 引擎。

### Implementation Decisions

**接缝。** 沿用唯一的接缝 `ext.Hook`；本则不新增接缝。supervisor 是这个接缝的**所有者**，不是新的一层。

- **新模块。** 插件 supervisor 从 `cmd` 移出来，成为 `internal` 下的一等模块：`cmd` 不能被窗口导入，
  而生命周期必须被窗口与命令风入口共享。选址：`internal/plugin`，依赖 `ext`，不依赖 `core/store`。
- **它拿到的是库的说法，不是库本身。** 启用名列表与角色解析结果由调用方读出来传进去：
  这样模块不需要文件、不需要索引，测试也不需要建库。
- **两段生命周期，各有一个理由。** 四个调用：`New(dir)` → `Resolve(roles)`（库打开**之前**：调度策略要参与索引重放，
  ADR 0007、存储布局，所以角色先解析、角色 runner 先预热）→ `Bind(host, enabled)`（库打开**之后**：填宿主提供者、
  加载启用列表）→ `Close()`。`Bind` 可重复：换新库只换提供者、按新的启用名增删 runner，同名 runner 不重建。
  两次调用都必须由同一处发起，今天的缺陷正是它们分别散在两个包里、且第二段在首次开库时不会发生。
- **宿主不再绑死在 runner 的构造上，而是一个提供者。** runner 每次能力调用问一次“现在的库是谁”。
  这是让“一个插件一个 runner”成立的关键：库出现之前就启动的 runner 不需要被关掉重开，
  “没有宿主”也变成准确的一句话（还没有库打开），而不是一个永久的错误。
- **一个插件名一个 runner。** 启用列表与角色解析共用同一份缓存；同一名字第二次被要求时返回同一个 runner。
- **失败要分归属。** 计入三次停用的只有插件自己的错：抛错、超时、超内存、返回结构非法、调用未声明的能力。
  宿主自身的错（写库失败、磁盘满）不计入，只记录，并原样回给插件——主流程的错不该由插件背锅停用。
  做法：宿主错误带标记出栈，回来时识别，不靠猜。
- **停用之后回退内置 runner**，与启动时插件起不来是同一条路（启动时已经如此，不新建机制）；
  回退写进 `Health`，不是静默换人。内置自己也起不来时没有第二级回退，`Health` 说清楚即可。
- **`Health` 是状态加原始原因**（正常 / 失败中 n / 已停用 / 起不来）。行标签走 i18n 目录，原因保持插件或宿主的原文，
  不给插件错误加翻译层；不加时间戳，界面用不上。
- **重新启用是一个用户动作、两个内部计数。** 设置页的那一个按钮同时做两件事：supervisor 清插件级计数并重开 runner，
  贡献层清隐藏集。两个计数器仍各自独立，互不合并。
- **预热只在角色上无条件发生**，其余启用插件惰性启动（今天已如此：贡献回调第一次被要求时才开）。
  语法错因此分两处暴露：角色插件在开库时、其余插件在首次使用，两者都进 `Health`。
- **运行时与角色。** 启用列表两种运行时都收（`on_event` 与贡献回调）；角色只收 js。
  这不是隐含约定，是 supervisor 里一条明确的拒绝与一条日志（ADR 0006：没有 exec 插件能跑通角色钩子）。
- **两层失败不合并。** 插件级（三次停用整个插件）在 supervisor；贡献级（三次隐藏一个命令或页面）留在贡献层。
  粒度不同：一个坏页面不该带走同一插件的命令（`plugins/ui.md` §8）。supervisor 是插件级唯一实现。
- **内置插件走同一条路。** `builtin` 的两个插件由 supervisor 认领，是它唯一知道内置名的位置；
  窗口与命令风入口都不再直接构造它们。
- **派生只有一条路。** supervisor 交出去的是同一个 `Deriver` 与同一个身份戳：窗口、智能体 API、
  `cards:write` 的能力调用用同一份。三处各自 new 一个 `cardSource` 的做法取消，
  “哪个插件在制卡”因此只被回答一次。
- **窗口的构造参数换成 supervisor。** 窗口向它要的是能力值与身份戳（`ext.Deriver`、`ext.Commander`…、`core.Producer`），
  不是 runner：runner 不外泄，“谁拥有运行期”因此在类型上成立，P2 把这条兑现得更彻底。
  不出现 `*ext.JSRunner`，也不出现“没有插件服务时自己造内置插件”的第二条路径。
  八个插件相关字段收缩为：一个 supervisor + `WithoutCards` / `WithoutScheduler`（既有测试用它强制走“没有插件”的回退）。
  开库回调改为构造参数：它必须在**首次**开库之前就位，今天它在那之后才注册，这正是缺陷 A。
- **依赖方向。** `cmd → internal/ui → internal/plugin → internal/ext → internal/core`。
- **ADR 0006 的一行措辞要改**：池的归属从“每扩展两个 runtime”改为“每 runner 两个，每扩展一个 runner”。不新增 ADR。

### Testing Decisions

好测试的标准沿用仓库既有口径：一条测试守一件事，删掉它必须能红。

- **先写的红测试**：启动路径开一次库，然后调用角色插件的 `remit.notes.get`，必须成功。
  今天的代码在这里是红的——它正是 A 的后果。
- 一个被启用又被设为角色的插件，runner 的构造次数为一。
- 三次失败之后 `Health` 报停用并带原因；第四次调用不进入引擎（用计数假件断言）。
- 切库：旧库的 runner 被关闭、新库的 runner 拿到新宿主；窗口不再持有旧 runner。
- 一个角色指向不存在或起不来的插件：库照常打开，角色回退内置，`Health` 说明原因。
- 换一个制卡插件后，经智能体 API 制的卡与经 `remit.cards.create` 制的卡带同一个 producer 戳。
  今天它们都是内置插件的戳，这条测试会红。
- **测试面**：supervisor 的接口，配假 runner 与假宿主。不需要引擎、不需要库目录、不需要窗口。
- **prior art**：`cmd/remit/extensions_test.go` 已经在用真插件目录测发现与启动，同级行为搬到 supervisor 上；
  `internal/ui/contrib_test.go` 的假 `CommandRunner` 是同一手法（测试用假件换掉引擎）。

### Out of Scope

- 退役 `exec` 运行时（ADR 0006 明确保留）。
- 让 `activation` 真正生效的惰性加载：仍按启用列表加载。
- 插件之间共享 runtime 池、跨库共享插件状态、机器级插件存储。
- 新的能力名或新的钩子。
- 设置页的视觉重做（只新增“停用与原因”这一行数据）。

### Further Notes

- A、B、C 三条缺陷建议先各写一条测试固定下来，再动结构——否则重构会把它们一起搬走而不被发现。
- 首次开库与切库的角色解析应该合成一个：开库 = 解角色 → 打开库 → 绑宿主 → 加载启用列表。
  今天角色解析只在启动时发生一次，切库时根本不发生。
- **交付切三笔，各自可回滚**：① A/B 的修复（一条能红的端到端测试 → 最小修复）；
  ② supervisor 抽出（新增模块、删掉五处入口，行为由 ① 与既有专项测试守）；
  ③ 健康可见（`Health` + 设置页一行 + 一个动作清两处计数）。① 不依赖后两笔。

## P2 · 钩子有类型：一处形状，两个适配器

### Problem Statement

钩子是字符串调用。每个钩子的入参与出参由调用方自己记得：派生结果在卡片模块，策略与完成文案在窗口，
命令答复与导入答复又各在一处，事件在启动代码里。契约产物 `remit.d.ts` 把这些形状再说一遍，
宿主却不校验它与 Go 是否一致。

后果是可验证的：ADR 0007 已经改过一次钩子名（`derive` → `deriveBlock`，`cards.render` 取消），
那次改动跨了五个包；想知道 `summary` 返回什么，只能去找调用点；一个只想测“模板渲染与派生字段如何相叠”的测试，
必须先在临时目录里写一份 `main.js` 并启动引擎。

### Solution

钩子的形状与钩子 ID 放在一处：每个钩子一个 Go 类型、一个 typed 方法；JS 与进程两个适配器在接缝处满足它。
契约产物从同一组类型生成，形状漂移由测试拦下，而不是靠作者记得。

### User Stories

1. 作为插件作者，我希望 `remit.d.ts` 里 `deriveBlock` 的返回形状就是宿主真正校验的那个形状。
2. 作为插件作者，我希望钩子改名时宿主与契约同时变，而不是其中一个落后一版。
3. 作为插件作者，我希望必备参数与可选参数在契约里看得出来，而不是全靠试。
4. 作为维护者，我希望一个钩子的形状只写一次，改它只改一个文件。
5. 作为维护者，我希望“这个钩子返回什么”能在代码里一眼找到，而不是从五个调用点反推。
6. 作为维护者，我希望增加一个钩子时，词汇表、类型、契约产物、fixtures harness 同步更新是被编译器要求的。
7. 作为 agent，我希望读一个文件就知道宿主与插件之间的全部数据形状，而不必跨包搜索。
8. 作为测试者，我希望用一个假实现替代整个插件，从而测卡片派生与模板渲染如何相叠。
9. 作为测试者，我希望 UI 的贡献测试不必启动 JavaScript 引擎。
10. 作为测试者，我希望 fixtures harness 仍能驱动任意声明过的钩子，即使某个钩子在 Go 里没有专属方法。
11. 作为用户，我希望插件升级后形状不匹配时，是这个插件降级，而不是整个复习流程出问题。

### Implementation Decisions

**接缝。** 仍是一个：`ext.Hook` 收窄为能力接口的组合。`Call` 从接口里消失，降为实现细节；**runner 本身不出 supervisor**——对外只交能力与身份戳。

- **形状表。** 每个钩子一对类型：入参与出参。字段名由 JSON 标签决定，Go 类型是唯一来源。
- **六个能力接口，不是一个宽接口。** `Deriver` / `Scheduler` / `Summariser` / `EventSink` / `Commander` / `Importer`，
  再由一个 `Hooks` 接口嵌起来。调用方各取所需（卡片只要 `Deriver`），测试替身只假一个方法。
- **`command` 一个钩子、两个方法。** 它一见两用：命令回调答结果，页面数据命令答节点树。
  `RunCommand` 返回宿主的 `CommandAnswer`；`PageData` 返回原始 JSON，由贡献层解析——
  贡献层已经导入 `ext`（它解析 `ext.Extension`），`ext` 不能反过来导入它，节点树也不搬进 `ext`。
- **入参是宿主形状，适配器做转换。** `ImportIn{Name, Data []byte, Format}`、`Type{ID, Fields, Version}`；
  调用方不碰 base64，不拼 `map[string]any`，不自己解码。
- **`describe` 进类型表，不进能力接口。** 它是线协议的问候，不是角色能力；业务代码无人调用，清单已带名与版本。
  进表才能让「词汇表里的每个钩子都有类型」这条完整性测试成立。
- **一张调用表。** 钩子 ID → 类型化调用闭包。类型化方法是表的薄包装；fixtures harness 与金标准也走这张表，
  因此“某个钩子在 Go 里没有专属方法”仍然可被 fixture 驱动，而字符串调用不再出现在业务代码里。
- **两个适配器，零逻辑。** 进程内与进程外各一个适配器，只做 JSON ↔ Go 的转换；
  能力检查、超时、内存、失败计数都在适配器之下的共用实现里，不在两个适配器里各写一遍。
- **契约从类型生成。** 字段、可选性、并集从 Go 类型反射；散文注释留在类型旁边，由生成器原样带出。
  并集用 struct tag 声明（`remit:"quiet|celebrated"`），生成器读它：不用注释指令（解析注释脆弱），
  也不在生成器里养第二张枚举表（那正是今天上下文类型表的毛病）。生成器不再为每个钩子手写签名。
- **`Call` 不对外。** 只有 fixtures harness 需要「按钩子名字、拿任意 JSON 跑一遍」：它走调用表，
  宿主代码里不再出现字符串调用。第三方插件的 fixtures 继续能驱动任意声明过的钩子。
- **过渡形状。** P1 的 runner 接口是过渡形态；P2 落地后它拆成能力接口，P1 的实现不用重写，只换交代的面。
- **交付切两笔。** ① 形状与适配器：新增类型与能力接口、`Call` 降私有、调用表、完整性与漂移测试——**不改行为**；
  ② 调用点：卡片、窗口、导入、贡献、启动代码换成能力接口，删掉窗口自己那个 `CommandRunner`。

### Testing Decisions

- 假 `Hooks` 让卡片与窗口的测试不再写 `main.js`、不再加载引擎；测的是“派生字段与类型模板如何相叠”这个行为。
- fixtures harness 的用例外形不变（`fixtures/<hook>/<case>.json` 与 expected 逐字比对），只把驱动方式换成调用表。
- 契约漂移测试保留，生成源换成类型反射；再加一条：删掉 Go 类型上的一个字段，`remit.d.ts` 必须变。
- 一条完整性测试：词汇表里的每个钩子 ID 在类型表里都有入参与出参；少一个就红。
- prior art：`internal/ext/exttest` 的逐字比对、`internal/ext/ts` 的漂移测试、`internal/golden` 的金标准。

### Out of Scope

- 新的钩子或新的能力（词汇表在 v1 是封闭的）。
- 插件作者可注册的模板过滤器。
- 为 `exec` 运行时补类型化能力的空缺（它只用同一组形状，不新增能力）。
- 契约产物的文档站、示例站。

### Further Notes

- 这一步之后，`remit.d.ts` 才真正是“生成物”，而不是“手写文件的漂移测试”。
- 若类型反射无法表达某个并集（例如 `tone` 的取值），在类型旁保留一个显式的枚举声明，由生成器读取；
  不要让生成器去猜字符串字面量。

## P3 · 上下文一张表：键、种类、读取

### Problem Statement

窗口上下文（十二个键）今天声明五遍：结构体、键列表、读取表、契约产物的类型表、以及回调 payload。
五处各有各的漏法：漏了结构体字段就编译不过；漏了读取表，表达式静默读成假；漏了类型表，契约里写成
`string | boolean`；漏了 payload，命令能按“有选中文本”出现，插件拿到回调却不知道有没有选中。
最后一条今天是真的：`note.selection`、`browse.selection`、`scope.active` 三个键能写进 `when`，却不在回调里。

### Solution

一张表：键 → 种类 → 读取函数。`when` 求值、回调 payload、契约产物都读它。加一个键是一次编辑。

### User Stories

1. 作为插件作者，我希望 `when` 能读到的每个键，在 `command` 与页面数据回调里也能读到。
2. 作为插件作者，我希望 `remit.d.ts` 里每个上下文键的类型是宿主真正的类型，而不是“字符串或布尔”。
3. 作为插件作者，我希望未知键被明确告警并读成假，而不是让整条贡献悄悄消失。
4. 作为插件作者，我希望新增一个上下文键时不必改五处，也不会因为漏一处而只在某个屏幕上出错。
5. 作为用户，我希望按“有选中文本”出现的菜单项，行为与它出现的原因一致。
6. 作为用户，我希望同一个插件页在同一个窗口状态下保持内容，窗口状态变了才重问。
7. 作为维护者，我希望上下文词汇表只有一个来源，宿主、契约、校验都从它派生。
8. 作为维护者，我希望给键加种类（枚举名）时，契约里的并集自动跟着变。
9. 作为 agent，我希望打开一个文件就能看到窗口上下文的全集及其含义。
10. 作为测试者，我希望一条表驱动测试覆盖全部键，而不是每个键一条。

### Implementation Decisions

**接缝。** 仍在贡献模块内：`contrib.Context` 从“结构体 + 四份并行清单”变成“结构体 + 一张表”。

- **一张表。** 每项：键名、种类（布尔 / 字符串 / 枚举及其名字）、读取函数。
- **派生而非并列。** 键列表、`when` 的读取、回调 payload 都从表派生；结构体保留（编译器可查、测试可构造），
  但不再是第二份清单。
- **payload = 表 + 每次调用附加的键**（当前笔记、当前卡片这类只在某次调用里成立的键）。
- **契约从种类生成。** 枚举键（mode、area、card.status）由种类带出并集；未知键的类型不再兜底成宽类型。
- **三个漏键从此进入 payload。** 这是对插件面的扩充，`apiVersion` 不动：契约从未对第三方发布，见
  [`plugins/system.md`](plugins/system.md) §2.4。
- **窗口照旧把状态填进结构体。** 这一步不改变窗口怎么算上下文，只改变它怎么被读出。
- **表就是顺序。** `ContextKeys` 按表的顺序输出，契约与未知键告警都依赖这个顺序；不再手写第二份序列。
- **种类只有三种**：布尔、字符串、枚举（带枚举名）。三种足够描述今天的十二个键；要加第四种时先问
  “能不能用一个枚举表达”。
- **交付一笔。** 表、派生、三个漏键、契约生成，一次改完；分开做会留下两份真实来源。

### Testing Decisions

- 一条表驱动测试：对表里的每个键，`when` 读出的值与 payload 里的值相同。
- 一条契约测试：每个键在 `remit.d.ts` 里都有且只有一行，类型与种类一致。
- 反向测试（能红的）：表里给一个键配空的读取函数，测试必须红——今天没有任何测试会在这种情况下变红。
- 现有 `when_test.go` 的语法与求值用例保留；新增的只有“词汇表完整”这一类。

### Out of Scope

- 新增上下文键（本则只统一来源；新键各有自己的产品理由）。
- 让 `when` 支持函数调用、正则或数值比较之外的运算。
- 上下文之外的调用参数（页面动作、导入格式等）的统一。

### Further Notes

- 三个漏键是缺陷，不是设计；落地时先加一条能红的测试（“选中文本时命令的回调里有 note.selection”）。

## P4 · 派生答案活过重建

### Problem Statement

派生答案的缓存在卡片模块里，而窗口的每一次写入都以重建它结束——评分也算写入。于是缓存只活到下一次写入，
命中率近乎零：同一块文本在一次复习里会被反复问。它之所以还对，恰恰是因为被扔掉：缓存的键只有块文本，
没有插件身份、没有卡片类型表的指纹。

后果：插件在渲染路径上被重复调用（ADR 0006 的修订正是在担心这一点），而“改一个卡片类型的字段”与
“换一个制卡插件”这两种失效，今天靠一次全量重建来保证，没有别的机制。

还有一条：智能体 API 的 source 是共享的，它的 resolver 会被多个 HTTP 处理 goroutine 同时到达，
而缓存 map 无锁——这不是“性能优化待做”，是一条活的竞态。

### Solution

给答案一个身份键（块文本 + 插件身份与修订 + 类型表指纹），让它活过重建；卡片模块接钩子接口，而不是具体 runner。

### User Stories

1. 作为复习的用户，我希望同一张卡片在一次会话里只被派生一次，翻回上一张时不重新算。
2. 作为复习的用户，我希望评分之后卡片面立刻正确，不需要等一次重算才显示。
3. 作为编辑笔记的用户，我希望改了块文本之后卡片面立刻跟着变。
4. 作为编辑卡片类型的用户，我希望改完字段或模板后，卡片面按新类型重算，而不是沿用旧答案。
5. 作为切换插件的用户，我希望换制卡插件后卡片面按新插件重算，旧插件的失败不被继承。
6. 作为用户，我希望一个插件出错时不要每一帧都重试，也不要让界面卡住。
7. 作为插件作者，我希望我的派生函数被调用的次数与块的数量相关，而不是与帧数相关。
8. 作为维护者，我希望缓存的失效是一条键，而不是一次全量重建。
9. 作为维护者，我希望缓存有明确上限，长会话不会无限增长。
10. 作为测试者，我希望用假钩子就能断言“问了几次”，不必启动引擎。

### Implementation Decisions

**接缝。** 卡片模块的入参从 `*ext.JSRunner` 换成 P2 的 `ext.Hooks`。

- **键。** 文本 + 插件 id 与修订 + 类型表指纹，一起摘要成定长键（32 字节）：长块文本不会把缓存的内存
  撑成文本的副本，等值比较也不扫全文。
- **并发是正确的底线。** 同一个 resolver 会被 HTTP 处理 goroutine 与窗口线程同时到达（智能体 API 的
  source 是共享的）。缓存自带互斥，`-race` 下并发请求必须干净——今天没有锁，先写这条测试。
- **两代，不是整批。** 有界（条目数固定），溢出丢上一代而不是全清：全清会让在屏的那一页在下一帧全部重问。
  与 runtime 池“满了就丢、不阻塞”同一手法。
- **寿命。** 缓存随库活，不随重建活：换类型表时重新编译模板但保留答案；键变了自然不命中。
- **失败也缓存。** 失败答案带插件身份一起缓存，换插件后不命中（ADR 0006 的修订要求失败同样不被重试）。
- **渲染与派生分开。** 模板编译属于类型表变化，答案缓存属于文本与插件；两者不再挤在同一个“重建”里。
- **回退不变。** 没有插件、没有答案、模板坏了，仍回退字段原文列表或块原文，不出白卡。

### Testing Decisions

- 评分一次之后，同一块文本不再调用钩子（计数假件）；今天这条会红，因为重建把缓存扔了。
- 并发：同一个 resolver 被多个 goroutine 同时问同一段与不同段文本，`-race` 必须干净。今天这条会红。
- 改类型字段 → 再问一次；换插件 → 再问一次。
- 失败被缓存：同一文本只问一次；换插件后重新问。
- 上限：喂入超过上限的文本，条目数不超上限；再问上一代的文本仍命中（行为断言，不断言内部结构）。
- 现有 `resolver_test.go` 的模板与回退用例保留，派生用例改用假钩子。
- prior art：`internal/cards/resolver_test.go`、`internal/ui/plugin_test.go`。

### Out of Scope

- 跨库或跨会话的持久缓存（派生答案不落库，ADR 0007/0008）。
- 后台预派生（例如打开笔记时预热整篇）。
- 卡片面的字节级缓存。

### Further Notes

- 这一则与 P1 有交集：runner 的生命周期一旦由 supervisor 拥有，“重建”就不再是失效手段，
  而是缓存必须自己说清键。两则分开做，但 P4 应排在 P1 之后。

## P5 · 插件页运行时：一个模块，不是窗口上的七方法八表

### Problem Statement

插件页的一生——进入、按上下文哈希命中、在飞时不再问、失败后重试、连续三次失败隐藏、库事件后失效——
是窗口上的七个方法与八张表。规则是真的、也是有价值的，但它没有接口：要测它只能造一个窗口，
于是唯一的守卫是一条从外面看的测试（“帧永不调用插件”）。

### Solution

一个页运行时模块持有每页的状态与规则：进入时回答“现在能画什么”，需要时安排一次后台作业，答案在下一帧被应用。
窗口只留一个字段。

### User Stories

1. 作为用户，我希望进入一个插件页时立刻看到上次的内容或骨架，而不是空屏等数据。
2. 作为用户，我希望同一个页面在同一个窗口状态下不重复闪烁加载。
3. 作为用户，我希望页面加载失败时看到原因与重试，而不是一张白页。
4. 作为用户，我希望页面连续失败三次后不再打扰我，并且设置页能告诉我为什么。
5. 作为用户，我希望写了笔记之后回到插件页，看到的是新数据而不是旧树。
6. 作为插件作者，我希望我的页面数据命令只被调用一次（同一上下文），而不是每帧一次。
7. 作为插件作者，我希望一个坏页面不带走我的命令与菜单项。
8. 作为维护者，我希望页面的状态机在一个文件里，能按状态读出来。
9. 作为维护者，我希望窗口只拥有一个字段，而不是八张表。
10. 作为测试者，我希望用假 runner 就能驱动整个状态机：命中、在飞、重试、隐藏、失效。

### Implementation Decisions

**接缝。** 贡献页运行时成为窗口与插件之间的一个模块；`pluginpage` 仍是无状态绘制。

- **模块位置与持有。** 页运行时是一个模块，放在窗口之下、贡献之上：持有每页的树、错误、在飞标记、
  上下文哈希、连续失败与隐藏集。`pluginpage` 只留视图态（高亮、标签页、折叠）——两者今天混在同一个 State 里。
- **接口**：进入（页面引用与上下文，回答“现在画什么”，并给一个可选的待跑作业）、应用（把作业的结果交回）、
  失效（库写入后）、健康（设置页读的原因与计数）、重新启用（清隐藏集）。具体签名在实现时定，不钉在稿里。
- **帧永不调用插件**：进入只读缓存并交出作业；作业在帧外跑；答案在下一帧被应用。纪律不变，位置从窗口移到模块。
- **作业是值，不是回调。** 进入交出的是一次调用（用它做什么、什么时候跑由窗口决定），模块不为窗口安排线程；
  这样模块测试里的“后台”就是直接调用，不需要自己造一个调度器。
- **两层失败不合并**：贡献级在这里（三次隐藏这一个页面），插件级在 P1（三次停用整个插件）。
- **失效的粒度**：库写入使所有页面的上下文哈希作废；窗口状态变化只让相关页面失配。
- **不引入新的绘制规则**：模块不产生控件、不读主题，只回答数据。
- **交付一笔**：状态搬迁、接口、失败与隐藏、设置页那一行一起。

### Testing Decisions

- 状态机可在没有窗口的情况下测：进入 → 命中 → 失效 → 重问；在飞时第二次进入不问；失败三次隐藏；重试失败一次后成功。
- “帧不调用插件”的守卫从窗口层移到模块层：一次帧级的读操作，插件调用次数为零。
- 设置页的“失败与隐藏”那一行从模块的 `Health` 读，测它不需要造页面。
- prior art：`internal/ui/contrib_test.go` 的假 `CommandRunner`、`internal/ext/contrib/failures_test.go` 的计数用例。

### Out of Scope

- 插件页的布局、控件与主题（`plugins/ui.md` 的绘制规则不变）。
- 页面的跨库缓存、页面之间的导航历史。
- 动作类节点（按钮、表单）的报送渠道——仍走命令钩子，不改形状。

### Further Notes

- 这一则是五项里最“内部”的一条：用户能感到的是不闪、不重复、失败有话说，其余是维护者的收益。
  排最后，因为它的接缝依赖 P1 的 runner 与 P2 的钩子接口。
