# 测试 · 只写能拦住回归的

`AGENTS.md` 的 Preference 里只有一句：一条测试的价值，等于它能捕获的 bug 有多真实。本稿把
这句话落成可判定的口径——什么算有效、无效的四种样子、清理时怎么决断。

## 1. 一条测试凭什么存在

测试不证明代码能跑，它证明改动没有把已经对的行为弄坏。所以它唯一的价值来源是**它可能变红
的那个 bug**。

| 问题 | 答不上来意味什么 |
|---|---|
| 哪种 bug 会让它红？ | 没有 bug 能让它红，它就不该存在 |
| 这个行为有没有别人在守？ | 重复只增加阅读成本和假信心 |
| 它红了，该改代码还是改测试？ | 答「改测试」的，多半在测实现 |

## 2. 无效测试的四种样子

| 样子 | 现场 | 为什么不算 |
|---|---|---|
| **测像素** | 断言坐标、宽高落在窗口内（`box.X+box.W > 720`） | 布局引擎的事；换组件或调字号就红，行为没变 |
| **测文案** | `tt.HasText("GNU AGPL-3.0")`，拿 `locales` 的静态标签做断言 | 测的是字符串常量；改一句人话就红 |
| **测实现** | 断言帧数、调用次数、私有结构 | 重构就红，而这类红灯训练人忽略红灯 |
| **重复** | 同一个检查复制到第五个文件，或把依赖自己的行为再断言一遍 | 多一份维护面，零新增防线 |

共同点：**它红了，你修的是测试而不是代码。** 这就是判定标准。

## 3. 有效测试认得出

- 一句话说清守的行为，失败信息能定位——「撤销后到期日回到原值」，不是「断言失败」。
- 守领域里真会破的东西：纯文本是真相、索引可重建、撤销不留痕、重放与增量一致、导入幂等。
- 状态分支用表格，而不是把同一段装配复制 N 份。
- 一条只守一件事，名字就是那件事。
- 在该行为所在的层测；拉起整个 app 只留给真正跨层的交互。

## 4. 清理口径

1. **先判断，再动手**：说不出一个会红的 bug 的测试进候选表；反过来，一个真实 bug 找不到
   测试守——记为缺口，另开票，不在清理里顺手补。
2. **默认删除**：`internal/ui` 的像素与静态文案断言是第一批。
3. **一次一包**：按包删，删完跑 `go test ./...`，全绿才继续。
4. **删完核对**：每个被删的测试，要么有另一个测试守同一行为，要么它的断言对象根本不是行为。
5. **只删不增**：不重排、不改名、不动生产代码、不换测试框架。
